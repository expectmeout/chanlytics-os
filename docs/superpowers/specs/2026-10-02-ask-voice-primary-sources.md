# Ask Voice against primary sources (2 Oct 2026)

Scope: the proposal to give Ask (the Chanlytics OS in-app assistant: a Next.js route that runs one Anthropic tool loop as the signed-in member and streams a structured answer whose `say` is prose and whose `show` is figures, rows and cards) a voice, by making it the custom LLM behind one ElevenLabs ElevenAgents voice agent, started from the browser with a server-minted token, with the voice conversation landing as ordinary turns of Ask's own thread. Every claim below is traced to the page that owns it. All pages were read on 2 October 2026 (the host's clock rolled over to 3 October while the reading was under way; the stamp stays 2 Oct). The URLs in the brief are one rename behind: the product is now ElevenAgents, the pages under `/docs/agents-platform/…` live under `/docs/eleven-agents/…` (and `server-tools` is now `webhook-tools`), the changelog is one page per entry (`/docs/changelog/2026/M/D`; 30 entries between 1 Apr and 28 Sep, 29 opened one by one, 23 Sep read from the index only), and the API reference sits under `/docs/api-reference/…` and `/docs/eleven-agents/api-reference/…`. The fetch tool summarises each page through a small model, so every field name or number that carries weight was checked with at least two differently worded prompts; a claim that no page states is marked UNKNOWN, and where two pages disagree both readings are given, not merged. First-party pages outside `/docs` (five blog posts, two product pages, two pricing pages) are used only where `/docs` is silent and are marked (blog), (product page) or (pricing page). Nothing here called the ElevenLabs API; the API-reference pages were read as documentation. The 3 Oct draft `docs/superpowers/specs/2026-10-03-ask-spoken-design.md` cites this note by section; where a source contradicts the draft, the section names the draft section it touches.

## Verdicts in twelve lines

1. Custom LLM contract: **CONFIRM** that an OpenAI-compatible SSE door is the documented way (Chat Completions or Responses, `data: [DONE]`, `user_id`, `elevenlabs_extra_body`, function calls for system tools); **CHANGE** the session carrier, because no page says a dynamic variable is templated into `elevenlabs_extra_body` (the extra body is its own client-sent `custom_llm_extra_body` behind its own Security toggle); **REFINE**: the request has no conversation id, a failing endpoint is retried at least 3 times and one turn may produce several requests, the URL suffix and the `api_key` header are unstated, and what happens to an in-flight request on barge-in is undocumented.
2. Starting a session: **CONFIRM** server-minted credentials with the API key never in the browser (WebRTC `conversationToken`, 10 minutes, returns `conversation_id`; WebSocket `signedUrl`, 15 minutes); **CHANGE** the draft's allowlist plus token pairing (the authentication page says to configure one, not both); **REFINE**: nothing the browser sends (`userId`, `dynamic_variables`, extra body) is verified, every override needs its own Security toggle, and `system__` variables cannot be sent.
3. Events: **CONFIRM** the set the Line needs (`user_transcript`, `agent_response`, `agent_response_correction`, `interruption`, `ping`, `vad_score`, `conversation_initiation_metadata`, `audio` on WebSocket only) and `contextual_update`, `user_message`, `user_activity` upstream; **REFINE**: `agent_chat_response_part` and `agent_response_complete` are opt-in through `client_events`, the `interruption` payload differs between two pages (`event_id` versus `reason`), and the API enum omits `agent_reasoning_response_part`.
4. SDKs: **REFINE**: React v1 needs a `ConversationProvider`; the React and JS pages document `startSession` with `agentId`, `signedUrl`, `conversationToken`, `userId` and `connectionType` only, so `dynamicVariables` (shown on the dynamic-variables page and in the Expo guide) and the extra-body option need confirming in the package types; React Native needs a development build (no Expo Go) with LiveKit modules.
5. Turn-taking: **CONFIRM** the knobs and their defaults (`turn_timeout` 7 s within 1 to 30, `turn_eagerness` normal, `speculative_turn` false, `turn_model` `turn_v3`, soft timeout off, `interruption` as a client event); **REFINE**: the soft-timeout filler is the platform-side twin of buffer words, and the draft's "about 1 s round trip, per the vendor" is on no page read (stated parts: orchestration under 100 ms (blog), Scribe v2 Realtime about 150 ms, Flash about 75 ms, v4 Turbo about 100 ms, v3 Conversational about 280 ms; marketing says sub-second).
6. Speech in and out: **CONFIRM** Scribe realtime as the agent ASR (`asr.provider: scribe_realtime`, `asr.keywords` up to 50) and a TTS enum of eight models (Flash v2 and v2.5, Turbo v2 and v2.5, Multilingual v2, v3 Conversational, v4, v4 Turbo; plain `eleven_v3` is not offered); **REFINE**: `agent.language` drives both ASR and TTS and only the LLM-called `language_detection` tool switches it, so "language detection on" needs the door to return that call (or a per-session `agent.language` override), and `text_normalisation_type: elevenlabs` lets Ask's `say` keep digits.
7. Text mode: **REFINE**: `conversation.text_only` is fixed per session at start (the override needs its toggle), chat-only sessions have their own pool (25 times voice) at $0.003 a message, typed messages inside a voice session are supported (`sendUserMessage`, widget voice plus text), and a text-only reply inside a voice session is UNKNOWN.
8. Privacy: **REFINE**: retention, audio saving and zero retention are per agent (`platform_settings.privacy.*`), not per member; two pages disagree on the default retention (2 years versus -1); `DELETE /v1/convai/conversations/{id}` is the per-conversation erase; the `post_call_transcription` webhook carries transcript, analysis, metadata and the initiation data including dynamic variables, signed with `elevenlabs-signature` (the HMAC details are not spelled out on the pages read).
9. Pricing and limits: **CONFIRM** $0.08 a minute beyond the plan, burst $0.16, text $0.003, plan minutes 15, 75, 275, 1,238, 3,738, 12,375 and concurrency 4, 6, 10, 20, 30, 40, LLM billed separately; **UNKNOWN**: whether a custom LLM carries any ElevenLabs LLM fee, any agent API rate limit, and where a concurrency refusal surfaces (mint or connect).
10. Testing: **REFINE**: `simulate-conversation` is deprecated in favour of agent tests (simulation, next reply, tool call) with `repeat_count` up to 50; whether tests or simulations call a custom LLM endpoint is not stated, so the draft's own door-level spoken evals stay the gate.
11. Latest releases: **CHANGE**: Speech Engine (25 May) is a first-party WebSocket bring-your-own-LLM product ($0.08 a minute) with the full history per turn and abort-on-interrupt; `api_type: websocket` joined the custom-LLM types on 3 Aug with no protocol page; `cascade_timeout_seconds` fell from 8 to 4 s on 20 Jul; the WebRTC token response gained a required `conversation_id` on 27 Jul.
12. MCP and workflows: **CONFIRM** neither is needed for a single in-app assistant whose tools run inside Ask; MCP approvals (Always Ask, fine-grained, No Approval; `awaiting_approval`, `approval_timeout_secs`) belong to the agent's own LLM and are unavailable under zero retention or HIPAA; workflows and agent transfer are per-agent graphs with nothing to add here.

## 1. The custom LLM contract

### What the source says

- The contract is two OpenAI shapes. The endpoint must mirror Chat Completions (`/v1/chat/completions`) or Responses (`/v1/responses`); the page says both are fully supported and both must answer with `Content-Type: text/event-stream`. Chat Completions: each chunk is `data: {json}` followed by a blank line and the stream ends with `data: [DONE]`; the page's chunk carries `id`, `object: "chat.completion.chunk"`, `created`, `model` and `choices[0]` with `delta.content`, `index` and `finish_reason: null`; its example servers relay upstream chunks unchanged, so the closing chunk's `finish_reason` is upstream's, and only `[DONE]` is stated as mandatory. Responses: each chunk is `event: {type}` then `data: {json}`, the minimum events are `response.output_text.delta` (field `delta`) and `response.completed` (`response.id`, `status: completed`), then `data: [DONE]`. https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm (read 2 Oct 2026)
- The request body in the page's examples: `messages` (a `system` message holding the agent prompt, the agent's first message as `assistant`, then the user turns), `model` (the Model ID typed into the dashboard), `temperature`, `max_tokens`, `stream: true`, `tools` (only when system tools are configured), `user_id` (optional; the example server renames it to OpenAI's `user`) and `elevenlabs_extra_body` (optional object). The Responses example models the request as `model`, `input[{role, content}]`, `instructions`, `temperature`, `max_output_tokens`, `stream`. No conversation id, session id or header naming one appears anywhere on the page. https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm (read 2 Oct 2026)
- Where `elevenlabs_extra_body` comes from: the WebSocket reference names the wire field `custom_llm_extra_body` inside `conversation_initiation_client_data` (the personalization page's example sets `temperature` and `max_tokens`), the custom-LLM page's Python example sets it client-side as `extra_body` in `ConversationInitiationData` (a `UUID` and two free keys) and shows it in the request as `elevenlabs_extra_body`; no single sentence states the mapping, but both ends are shown. The agent must opt in with `platform_settings.overrides.custom_llm_extra_body` (boolean, default false). Dynamic variables are documented for system prompts, first messages, tool parameters and tool headers; no page says a variable is templated into the request body, the extra body or the LLM request headers. First-party practice (blog): pass the identifier inside the extra body and read `req.elevenlabs_extra_body` on the server. https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm and https://elevenlabs.io/docs/eleven-agents/customization/personalization and https://elevenlabs.io/docs/eleven-agents/customization/personalization/dynamic-variables and https://elevenlabs.io/docs/api-reference/agents/create and https://elevenlabs.io/blog/practical-guide-open-source-agent-frameworks-and-elevenagents (read 2 Oct 2026)
- Agent-side fields, `conversation_config.agent.prompt.custom_llm`: `url` (required; described as the Chat Completions compatible endpoint), `model_id`, `api_key` (a workspace secret `{secret_id}` or an environment variable `{env_var_label}`), `auth_connection` (only connections that produce an Authorization Bearer token; Basic, mTLS, custom-header and URL-secret connections are not supported), `request_headers` (a map of header name to value; the value type is not shown), `api_version`, `api_type` (`chat_completions` by default, `responses`, `websocket`). No page says which header `api_key` rides in, or whether ElevenLabs appends `/chat/completions` to `url`: the four provider walkthroughs enter base URLs ending `/v1` (Groq `https://api.groq.com/openai/v1`, Together `https://api.together.xyz/v1`, SambaNova `https://api.sambanova.ai/v1`, Cloudflare `…/ai/v1/`), while the custom-LLM page's own server listens on `/v1/chat/completions`. The URL and the key may be environment variables (`{{system__env_<label>}}`, `env_var_label`), picked per session by `environment`. https://elevenlabs.io/docs/api-reference/agents/create and https://elevenlabs.io/docs/api-reference/agents/get and https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm/groq-cloud and https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm/together-ai and https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm/samba-nova-cloud and https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm/cloudflare and https://elevenlabs.io/docs/eleven-agents/integrate/environment-variables (read 2 Oct 2026)
- Sampling and reasoning fields: the agent's `temperature` defaults to 0 and null omits it from the LLM request (18 May entry); `max_tokens` defaults to -1 (only a value above 0 caps output; the walkthrough sets Limit token usage to 5000); `reasoning_effort` (`none` up to `max`), `thinking_budget` and `enable_reasoning_summary` exist. A custom endpoint must return reasoning separately (`reasoning` or `reasoning_content` in each delta; Responses: a `reasoning` output item with `summary`); ElevenLabs never derives it from the answer. https://elevenlabs.io/docs/api-reference/agents/create and https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm and https://elevenlabs.io/docs/changelog/2026/5/18 (read 2 Oct 2026)
- Timeouts. No page gives an HTTP, first-byte or total-duration limit for a custom LLM. `cascade_timeout_seconds` (agent field; default 4, range 2 to 15; the default was 8 until the 20 Jul entry) is described as the time before cascading to a backup LLM. The cascading page says a custom LLM is retried against the same endpoint (at least 3 attempts) and never falls back to ElevenLabs-hosted models, and lists API errors, timeouts and empty responses as the failures. Whether the timer means first byte, first sentence or the whole answer is not stated, and what the conversation does after the last failed attempt is not stated (the LLM page warns that with backups disabled a failing primary ends the conversation abruptly). https://elevenlabs.io/docs/api-reference/agents/create and https://elevenlabs.io/docs/eleven-agents/customization/llm/llm-cascading and https://elevenlabs.io/docs/eleven-agents/customization/llm and https://elevenlabs.io/docs/changelog/2026/7/20 (read 2 Oct 2026)
- Several requests per turn (blog): the orchestrator predicts when the user has finished speaking and in some cases sends multiple generation requests with the same conversation context inside one turn. The agent field `speculative_turn` (default false) is documented as starting LLM generation during silence. https://elevenlabs.io/blog/unpacking-elevenagents-orchestration-engine and https://elevenlabs.io/docs/api-reference/agents/create (read 2 Oct 2026)
- Buffer words, the page's technique for a slow endpoint: the page says to "return an initial response ending with" an ellipsis followed by exactly one space (`... `); that lets the TTS keep natural prosody while the real answer is generated, and the trailing space matters because without it the next chunk is appended to the dots and the audio distorts. The page's example streams a short think-aloud sentence ending `... ` as the first `delta.content` (`id: chatcmpl-buffer`, `finish_reason: null`) before the real stream. https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm (read 2 Oct 2026)
- Tool calls. System tools are added to `tools` automatically when they are configured on the agent (the page's sample request lists `end_call`, `language_detection`, `skip_turn`); the endpoint answers in OpenAI function-call form, `{type: function, function: {name, arguments}}` with `arguments` a JSON string. Documented parameters: `end_call` (`reason` required, `message`), `language_detection` (`reason` and `language`, both required), `transfer_to_agent` (`reason`, `agent_number` required), `transfer_to_number` (`reason`, `transfer_number`, `client_message`, `agent_message` required), `skip_turn` (`reason`), `voicemail_detection` (`reason` required), plus `play_keypad_touch_tone` and `update_state` on the system-tools page. The page requires function-calling support for them, shows no streamed (`delta.tool_calls`) encoding, and says nothing on whether client, webhook or MCP tools are sent to a custom LLM, or what the agent does when the LLM ignores a tool. Dashboard-created agents get `end_call` by default; API-created ones do not. `enable_parallel_tool_calls` (default true) arrived 21 Sep. https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm and https://elevenlabs.io/docs/eleven-agents/customization/tools/system-tools and https://elevenlabs.io/docs/eleven-agents/customization/tools/system-tools/end-call and https://elevenlabs.io/docs/changelog/2026/9/21 (read 2 Oct 2026)
- History. The example request carries the conversation so far on every turn; no cap or truncation rule is stated; the cost page recommends history summarisation or a sliding window for stateful conversations, which implies full replay by default. The Speech Engine upstream states it sends the full history up to and including the latest user turn. https://elevenlabs.io/docs/eleven-agents/customization/llm/custom-llm and https://elevenlabs.io/docs/eleven-agents/customization/llm/optimizing-costs and https://elevenlabs.io/docs/eleven-agents/api-reference/speech-engine-upstream/speech-engine-upstream (read 2 Oct 2026)
- Interruption. Nothing on the custom-LLM, events or cascading pages says whether ElevenLabs closes or ignores an in-flight HTTP request when the user barges in. The Speech Engine docs say their SDK cancels the in-flight LLM request through an `AbortSignal` and that responses carrying an outdated `event_id` are discarded. https://elevenlabs.io/docs/overview/capabilities/speech-engine and https://elevenlabs.io/docs/eleven-agents/api-reference/speech-engine-upstream/speech-engine-upstream (read 2 Oct 2026)
- Extras. The `agent_response_metadata` client event is documented as custom-LLM-only and opt-in through `client_events`, but no page says how the endpoint supplies the metadata. `api_type: websocket` joined the custom-LLM types on 3 Aug 2026 with no protocol page. The static egress IP page lists post-call webhooks, Speech Engine, MCP and webhook-tool traffic, and does not list custom-LLM requests. https://elevenlabs.io/docs/eleven-agents/customization/events/client-events and https://elevenlabs.io/docs/changelog/2026/8/3 and https://elevenlabs.io/docs/eleven-api/resources/ip-allowlisting (read 2 Oct 2026)

### What it means for the design

- **CONFIRM** the door's shape: `POST`, `Content-Type: text/event-stream`, Chat Completions chunks whose `delta.content` is the `say` text only (no JSON, no `show`, no reasoning), a closing chunk with `finish_reason: "stop"`, then `data: [DONE]`. Never end a stream empty: an empty response is a documented failure that triggers a retry, so a refusal must still speak its words.
- **CHANGE** (draft §3.3) the carrier of the session id: the sources document `custom_llm_extra_body` arriving as `elevenlabs_extra_body` (with `platform_settings.overrides.custom_llm_extra_body: true`), not a dynamic variable templated into it. Two documented-path options: send `custom_llm_extra_body: {chanlytics_session}` straight from the browser (confirm the SDK forwards it, §4), or put `{{chanlytics_session}}` in the agent's system prompt so the resolved text arrives in `messages[0]` (an inference from the dynamic-variables page plus the request example; prove it in the spike). Treat `user_id` as a label, never as identity.
- **REFINE** the path and the secret: serve one handler at the configured path and also at `…/chat/completions` and `…/v1/chat/completions` (an optional catch-all) and log the first request's path, because no page says whether a suffix is appended; carry the agent secret in `request_headers` (a custom header) or in `api_key` and confirm on the first call which header it arrives in.
- **REFINE** retries: expect at least 3 identical requests on a slow or failing turn and, per the blog, several requests with the same context inside one turn, so dedupe on (session, last user message) and store a turn once; keep `speculative_turn` false; send the first chunk at once (the trace label, or buffer words `... `) so the first byte is never the model's. Whether the 4 s `cascade_timeout_seconds` means first byte is unstated: measure, and raise toward 15 if the spike shows retries.
- **REFINE** tools (draft §3.3, §3.7): with no system tool configured nothing arrives in `tools`; if `language_detection` or `end_call` is switched on, the agent acts only when the door returns a function call, so "ignore tools" and "language detection on" cannot both hold. The page does not say that the agent then simply speaks.
- **UNKNOWN** what ElevenLabs does to an in-flight request on barge-in: the draft's choice to run the turn to its end and store it whole is safe either way, provided duplicates are deduped.

## 2. Starting a session as a specific signed-in user

### What the source says

- Signed URL (WebSocket): `GET https://api.elevenlabs.io/v1/convai/conversation/get-signed-url?agent_id=…` with header `xi-api-key`; the response field is `signed_url`; it is valid for 15 minutes to open a connection, an open socket survives expiry, a new connection with an expired URL fails; there is no limit on how many are minted and ElevenLabs recommends a new one per user session. Other query parameters: `include_conversation_id` (default false; when set the conversation signature cannot be reused), `branch_id`, `version_id`, `environment` (default `production`), `debug_events_request`; `agent_id` also accepts a Speech Engine external id. https://elevenlabs.io/docs/eleven-agents/customization/authentication and https://elevenlabs.io/docs/api-reference/conversations/get-signed-url (read 2 Oct 2026)
- Conversation token (WebRTC): `GET /v1/convai/conversation/token?agent_id=…` (also `participant_name`, which defaults to the user id, `branch_id`, `version_id`, `environment`) returns `{token, conversation_id}`; `conversation_id` has been a required response field since 27 Jul 2026; the Kotlin page says the `conversationToken` is valid for 10 minutes, and the API page gives no expiry. https://elevenlabs.io/docs/api-reference/conversations/get-webrtc-token and https://elevenlabs.io/docs/eleven-agents/libraries/kotlin and https://elevenlabs.io/docs/changelog/2026/7/27 (read 2 Oct 2026)
- Transport rule in the SDKs: voice sessions use WebRTC and text-only sessions use WebSocket by default; `connectionType` (`'webrtc'` or `'websocket'`) can force either; `signedUrl` authorises WebSocket and `conversationToken` authorises WebRTC; the API key is needed only to mint and must never reach the client; regional base URLs are `api.us.elevenlabs.io`, `api.eu.residency.elevenlabs.io`, `api.in.residency.elevenlabs.io`, `api.sg.residency.elevenlabs.io`. https://elevenlabs.io/docs/eleven-agents/libraries/java-script and https://elevenlabs.io/docs/eleven-agents/libraries/react and https://elevenlabs.io/docs/api-reference/conversations/get-signed-url (read 2 Oct 2026)
- Agent auth: `platform_settings.auth.enable_auth` (default false; when true a signed token is required to start a conversation); `platform_settings.auth.allowlist` (hostnames; up to 10; exact match, subdomains added separately; checked against the request origin). The authentication page says not to configure signed URLs and allowlists together on one agent, and that a signed URL only proves the request came from an authorised source, so per-user checks belong in your app; it does not mention conversation tokens or whether the allowlist applies to WebRTC. https://elevenlabs.io/docs/eleven-agents/customization/authentication and https://elevenlabs.io/docs/api-reference/agents/create (read 2 Oct 2026)
- The initiation payload (first client message on a WebSocket; the SDKs build it from `startSession` options): `type: conversation_initiation_client_data`, `conversation_config_override` {`agent` {`first_message`, `language`, `max_conversation_duration_message`, `prompt` {`prompt`, `llm`, `tool_ids`, `native_mcp_server_ids`, `knowledge_base`}}, `tts` {`voice_id`, `model_id`, `stability`, `speed`, `similarity_boost`, `supported_voices`, `pronunciation_dictionary_locators`}, `conversation` {`text_only`, `max_duration_seconds`}, `asr` {`keywords`}, `turn` {`soft_timeout_config`}}, `custom_llm_extra_body`, `dynamic_variables` (string, number, integer or boolean), `user_id`, `source_info`, `branch_id`, `environment`, `starting_workflow_node_id`, `procedure_ids`. Variables prefixed `system__` cannot be sent. https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket and https://elevenlabs.io/docs/eleven-agents/customization/personalization and https://elevenlabs.io/docs/eleven-agents/customization/personalization/dynamic-variables (read 2 Oct 2026)
- Which overrides must be enabled: each overridden field needs its Security-tab toggle (dashboard list: first message, system prompt, tools, knowledge base, ASR keywords, LLM; API: `platform_settings.overrides.conversation_config_override.*`, which also holds `agent.language`, `tts.voice_id`, `tts.stability`, `tts.speed`, `tts.similarity_boost`, `tts.model_id`, `conversation.text_only`, `conversation.max_duration_seconds`, `asr.keywords`, `turn.*`), plus `platform_settings.overrides.custom_llm_extra_body` and `…enable_conversation_initiation_client_data_from_webhook`. An override on a field whose toggle is off raises an error (ASR keywords are dropped silently); no toggle is documented for `dynamic_variables` or `user_id`; the overrides page steers people to dynamic variables rather than prompt overrides. The dashboard list omits language, voice and model, which the API shape includes, and the overrides page's field list omits `tts.model_id`, `conversation.max_duration_seconds` and `turn.*`, which the API and the 20 Jul and 10 Aug entries add. https://elevenlabs.io/docs/eleven-agents/customization/personalization/overrides and https://elevenlabs.io/docs/api-reference/agents/create and https://elevenlabs.io/docs/eleven-agents/guides/chat-mode (read 2 Oct 2026)
- The initiation webhook (Fetch initiation client data from a webhook) serves telephony and messaging channels and does not run for widget or SDK conversations. https://elevenlabs.io/docs/eleven-agents/customization/personalization (read 2 Oct 2026)
- Identity fields: `userId` (React, Kotlin, Swift) and Python's `start_session(user_id=…)` map a conversation to a person and ElevenLabs recommends passing your own end-user ids; the Users view groups by it with exact-match search; no page says it is verified; the 4 May entry says `@elevenlabs/react@1.2.2` generates a random user id automatically. Pages disagree on the signed URL's query parameter: the authentication page shows `conversation_signature`, the WebSocket guide shows `token`. https://elevenlabs.io/docs/eleven-agents/libraries/react and https://elevenlabs.io/docs/eleven-agents/libraries/python and https://elevenlabs.io/docs/eleven-agents/operate/users and https://elevenlabs.io/docs/changelog/2026/5/4 and https://elevenlabs.io/docs/eleven-agents/libraries/web-sockets (read 2 Oct 2026)
- Environments: an `environment` value on the token request, the WebSocket query or the React hook selects per-environment values; the custom LLM URL and key may be environment variables. Browser prerequisites: request the microphone with `navigator.mediaDevices.getUserMedia({audio: true})` before `startSession`; the Next.js quickstart mints in `app/api/get-signed-url/route.ts`, uses `'use client'` components and a `ConversationProvider` in the page. https://elevenlabs.io/docs/eleven-agents/integrate/environment-variables and https://elevenlabs.io/docs/eleven-agents/guides/quickstarts/next-js (read 2 Oct 2026)

### What it means for the design

- **CONFIRM** the minting flow: the edge holds `ELEVENLABS_API_KEY`, mints per member, the browser holds one token; for voice the WebRTC token is the default and the signed URL is for text-only WebSocket. The token is good for 10 minutes to start (one page), so start the session at once and mint again on retry.
- **REFINE** the mint response: return `conversation_id` (required in the token response since 27 Jul) with `session`, store it on `ask_voice_sessions`, and match the post-call webhook by `data.conversation_id` as well as by the dynamic variable.
- **CHANGE** (draft §3.7) the domain allowlist: with `enable_auth: true` and tokens minted per member the allowlist is not needed, and the page says not to combine them. Pick tokens; drop the allowlist.
- **REFINE** overrides: switch on only what the browser sends (`custom_llm_extra_body`; `agent.first_message` for Read aloud; `agent.language` if the language is chosen per session) and leave `prompt`, `llm`, `tool_ids`, `knowledge_base` off, so a tampered browser cannot change the agent. A first-message length limit is UNKNOWN.

## 3. Client events and client-to-server events

### What the source says

- Transport. Client events are described as part of the WebSocket protocol, handled by the SDKs; over WebRTC the `audio` event is not sent because LiveKit carries the audio; the events overview names only WebSockets and says nothing about how the other events travel on WebRTC. https://elevenlabs.io/docs/eleven-agents/customization/events/client-events and https://elevenlabs.io/docs/eleven-agents/customization/events (read 2 Oct 2026)
- Server to client, the core set: `conversation_initiation_metadata` → `conversation_initiation_metadata_event {conversation_id, agent_output_audio_format, user_input_audio_format}`; `user_transcript` → `user_transcription_event {user_transcript, event_id}` (final text only); `agent_response` → `agent_response_event {agent_response, event_id, response_id, in_response_to_ids, response_type: text | voice, attachments[{url, name, mime_type}]}` (in voice it usually arrives after the audio has started); `agent_response_correction` → `agent_response_correction_event {original_agent_response, corrected_agent_response, event_id, response_id}` (the truncated text after an interruption); `audio` → `audio_event {audio_base_64, event_id, alignment {chars, char_start_times_ms, char_durations_ms}, is_final}`; `ping` → `ping_event {event_id, ping_ms}`, answered by `pong {event_id}`; `vad_score` → `vad_score_event {vad_score}` (0 to 1); `client_tool_call` → `client_tool_call {tool_name, tool_call_id, parameters, event_id, expects_response}`. https://elevenlabs.io/docs/eleven-agents/customization/events/client-events and https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket (read 2 Oct 2026)
- `interruption`: the API reference gives `interruption_event {event_id}`; the WebSocket guide gives `interruption_event {reason}`; the client-events page does not list the event; the conversation-flow page says interruptions are enabled by selecting `interruption` as a client event. The pages disagree on the payload. https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket and https://elevenlabs.io/docs/eleven-agents/libraries/web-sockets and https://elevenlabs.io/docs/eleven-agents/customization/conversation-flow (read 2 Oct 2026)
- Opt-in events, chosen in `conversation_config.conversation.client_events` (the API enum: `conversation_initiation_metadata`, `asr_initiation_metadata`, `ping`, `audio`, `interruption`, `user_transcript`, `tentative_user_transcript`, `agent_response`, `agent_response_correction`, `client_tool_call`, `mcp_tool_call`, `mcp_connection_status`, `agent_tool_request`, `agent_tool_response`, `agent_tool_response_full_payload`, `agent_response_metadata`, `vad_score`, `agent_chat_response_part`, `client_error`, `guardrail_triggered`, `dtmf_request`, `agent_response_complete`, `context_usage`, `internal_turn_probability`, `internal_tentative_agent_response`): `agent_chat_response_part` → `text_response_part {type: start | delta | stop, text, event_id, response_id}` (always sent in text-only sessions, opt-in in voice, not sent under a blocking guardrail); `agent_response_complete` → `{event_id}` (fires when the response, pending tool calls included, is finished); `agent_response_metadata` → `{metadata, event_id}`; `agent_tool_response_full_payload` (`full_tool_result` string, 64 KB cap, may expose sensitive data); `context_usage` → `{event_id, model, context_tokens, context_limit_tokens}`; `guardrail_triggered`. `queue_status` (`waiting`, `admitted`, `timed_out`; close code 4300) is always sent to queued callers. The default `client_events` set is not stated on any page read. `agent_reasoning_response_part` (experimental, text-only) is described as opt-in but is absent from the API enum, and `tentative_user_transcript` is in the enum but described nowhere; the pages disagree there. https://elevenlabs.io/docs/eleven-agents/customization/events/client-events and https://elevenlabs.io/docs/api-reference/agents/create and https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket (read 2 Oct 2026)
- Client to server (WebSocket `type` strings, SDK helpers in brackets): `user_audio_chunk` (a base64 string under that key, no `type`); `user_message {text}` (the API reference adds `id`, `user_identifier`, `source_medium: audio | dtmf | text | image | file`) [`sendUserMessage`], processed as if spoken and triggering a turn; `contextual_update {text, context_id?}` [`sendContextualUpdate`], non-interrupting background context where a newer update with the same `context_id` supersedes an older one (turns store `contextual_update_info {context_id, is_superseded}`); `user_activity` [`sendUserActivity`], which resets the turn timeout and changes nothing else (the JS page says the agent will not try to speak for at least 2 seconds; the widget limits it to once a second since 0.18.2); `pong {event_id}`; `client_tool_result {tool_call_id, result, is_error, error_type?}`; `feedback {event_id, score}`; `multimodal_message` (up to 5 `file_id`s); `mcp_tool_approval_result {tool_call_id, is_approved}`. https://elevenlabs.io/docs/eleven-agents/customization/events/client-to-server-events and https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket and https://elevenlabs.io/docs/eleven-agents/libraries/java-script and https://elevenlabs.io/docs/changelog/2026/9/14 (read 2 Oct 2026)
- Mode and level signals. The protocol has no mode event; the SDKs derive `mode` (`speaking`, `listening`) and `status` (`disconnected`, `connecting`, `connected`); output level comes from `getOutputVolume()` (0 to 1) and `getOutputByteFrequencyData()`; in WebRTC the audio format is fixed at `pcm_48000`, so frequency data differs from WebSocket sessions; WebSocket audio formats default to `pcm_16000` (options `pcm_8000` to `pcm_48000`, `ulaw_8000`). https://elevenlabs.io/docs/eleven-agents/libraries/java-script and https://elevenlabs.io/docs/eleven-agents/libraries/react and https://elevenlabs.io/docs/api-reference/agents/create (read 2 Oct 2026)
- Correlation detail: the 9/14 entry says iOS now reconciles agent messages by `response_id` instead of `event_id`, because several responses can surround tool calls; `agent_response.attachments` arrived on 7 Sep. https://elevenlabs.io/docs/changelog/2026/9/14 and https://elevenlabs.io/docs/changelog/2026/9/7 (read 2 Oct 2026)

### What it means for the design

- **CONFIRM** the draft's event mapping (§3.5): `user_transcript` is the question, `agent_response` and `agent_chat_response_part` the live say, `agent_response_correction` the words actually spoken, `vad_score` and `getOutputVolume()` the three's `hear` and `voice`.
- **REFINE** provision `client_events` explicitly: `interruption`, `user_transcript`, `agent_response`, `agent_response_correction`, `agent_chat_response_part`, `agent_response_complete`, `vad_score` (and `audio` only where the transport is WebSocket); do not rely on defaults the pages never state.
- **REFINE** key on the `interruption` event type, not its payload (the pages disagree), and pair it with `agent_response_correction`; the durable record of what was cut is the post-call transcript's `interrupted` flag and `original_message`.
- **REFINE** "the response's end": over WebRTC there is no `audio.is_final`; candidates are `agent_response_complete` (whether it marks the end of generation or of speech is unstated) and the `stop` part. Keep the draft's rule that the stored turn is read from the thread after the stream and that events only drive the live view.
- **UNKNOWN** how a custom LLM supplies `agent_response_metadata`, so `show` must reach the screen by the thread read, as the draft has it. Do not send `contextual_update` for page context: Ask already holds it, and how an update appears in the `messages` the door receives is unstated.

- **UNKNOWN** whether ElevenLabs' tag, normalisation and multi-voice prompt additions reach a custom LLM; the door should never emit tags or markup.

## 7. Text mode and multimodality

### What the source says

- Text-only is a session property: `conversation_config.conversation.text_only` (default false; audio is not processed) or the per-session override `conversation.text_only` (`textOnly` in the SDKs), which needs its Security toggle; text-only sessions request no microphone, create no audio context, default to WebSocket, and need `agent_response` in `client_events` or the replies are not delivered. iOS SDK 3.2.0 added text-only over WebSockets (18 May). https://elevenlabs.io/docs/eleven-agents/guides/chat-mode and https://elevenlabs.io/docs/eleven-agents/libraries/react and https://elevenlabs.io/docs/changelog/2026/5/18 (read 2 Oct 2026)
- Chat-only concurrency is a separate pool: Free 100, Starter 150, Creator 250, Pro 500, Scale 750, Business 750 (voice 4, 6, 10, 20, 30, 30), described as 25 times voice; during the handshake a chat-only session counts against the total limit first. The pricing page shows Business voice concurrency 40 where the chat-mode and models pages show 30; the pages disagree. https://elevenlabs.io/docs/eleven-agents/guides/chat-mode and https://elevenlabs.io/pricing/agents and https://elevenlabs.io/docs/overview/models (read 2 Oct 2026)
- Typed messages in a voice session: `sendUserMessage(text)` (the JS page: sends a text message to the agent) and the WebSocket `user_message`, which the events page says triggers the same response flow as spoken input; the widget supports voice plus text in one session (users can switch between voice and text), with a text-only mode when a conversation is started by text. `agent_response.response_type` is `text` or `voice` and is never explained; a text-only reply inside a voice session is not documented. https://elevenlabs.io/docs/eleven-agents/libraries/java-script and https://elevenlabs.io/docs/eleven-agents/customization/widget and https://elevenlabs.io/docs/eleven-agents/api-reference/eleven-agents/websocket (read 2 Oct 2026)
- Text channels (Slack, widget, WhatsApp, Zendesk, SMS) can be tuned with `text_behavior_overrides.[channel]`: `verbosity` (Auto, Concise, Thorough), `output_format` (plain text, Markdown), `interaction_budget` (`realtime`, `5_minutes`, `10_minutes`, `1_hour`); voice always uses a realtime budget. https://elevenlabs.io/docs/eleven-agents/customization/channel-behavior (read 2 Oct 2026)
- Billing: text-only is billed per message ($0.003 on the pricing page); a multimodal call is billed by duration plus per message; LLM cost is passed through separately. https://elevenlabs.io/pricing/agents and https://elevenlabs.io/docs/help-center/product/eleven-agents/how-much-does-eleven-agents-cost (read 2 Oct 2026)
- Files: `conversation_config.conversation.file_input` (`enabled` default true, `max_files_in_memory` default 10, `max_files_per_conversation`), images and PDFs only when the model supports them; `sendMultimodalMessage` with `fileIds` (31 Aug). https://elevenlabs.io/docs/eleven-agents/customization/multimodal-input and https://elevenlabs.io/docs/changelog/2026/8/31 (read 2 Oct 2026)

### What it means for the design

- **CONFIRM** the draft's rule that typing leaves voice and goes through Ask's own route (§2): a text-only ElevenLabs session would add a hop and $0.003 a message for no gain.
- **REFINE** Today's Listen: `sendUserMessage("Brief me on today")` right after the session starts is a documented path in a voice session, with the spoken reply; leave `first_message` empty so the agent waits (the API says an empty first message makes it wait).
- **REFINE** Read aloud: the documented path is the `agent.first_message` override (toggle on); its length limit is UNKNOWN, so keep the fallback to the speech port for long answers.
- **UNKNOWN** a text-only answer inside a voice session; do not build on it.

### What it means for the design

- **CHANGE** the architecture note (draft §1, §3): the draft treats the HTTP custom LLM as the only door; Speech Engine is a first-party alternative with a documented protocol, the full history on every turn, a defined cancel-on-interrupt, a persistent socket and the same $0.08 a minute. It needs a long-lived public WebSocket server, which a request-response route on the dashboard's serverless host does not provide (an inference about hosting, not an ElevenLabs statement), so the HTTP door stays the V1 choice and Speech Engine is the named V2 option if first-word latency or duplicate requests hurt.
- **REFINE** (draft §8.3) "sentence pipelining through the WebSocket text input": no page documents a separate text-input channel into an agent's TTS; the only incremental text paths documented are the custom-LLM stream itself and Speech Engine's `agent_response` chunks.
- **REFINE** `cascade_timeout_seconds`: 8 became 4 on 20 Jul, so older advice on slow endpoints is off by a factor of two; set it explicitly (2 to 15) and send the first chunk early.
- **REFINE** `api_type: websocket` and the self-hosted orchestrator: both exist, neither is documented; do not build on either.
- **UNKNOWN** the meaning of `eleven_realtime_v1_mini` and whether it touches agents.

## Changes to the design, ranked

1. **Session carrier**: no documented templating of a dynamic variable into `elevenlabs_extra_body`; send `custom_llm_extra_body` (needs `platform_settings.overrides.custom_llm_extra_body`) or place the variable in the system prompt, and confirm the SDK option name first. (§1, §2, §4)
2. **Allowlist and token**: do not configure both; use `enable_auth: true` with minted tokens and drop the allowlist. (§2)
3. **Language**: "language detection on" and "tools ignored" cannot both hold; the tool only acts if the door returns a function call; otherwise set `agent.language` per session or stay single-language. (§1, §6)
4. **Door path and secret**: serve the handler at the bare path and at `…/chat/completions` and `…/v1/chat/completions`; confirm the secret's header on the first call. (§1)
5. **Duplicates and retries**: dedupe on (session, last user message); at least 3 retries on the same endpoint and possibly several requests per turn; never end a stream empty. (§1)
6. **`client_events`**: provision the list explicitly with `interruption`, `user_transcript`, `agent_response`, `agent_response_correction`, `agent_chat_response_part`, `agent_response_complete`, `vad_score`. (§3, §5)
7. **Round-trip claim**: remove "about 1 s per the vendor"; no page states it. (§5)
8. **Mint response**: return `conversation_id` with the token and store it for webhook matching; the token is good for 10 minutes. (§2)
9. **Soft timeout and `cascade_timeout_seconds`**: set both explicitly (3.0 s filler; timeout toward 15 s) and send the first chunk early. (§1, §5, §11)
10. **Text normalisation**: set `text_normalisation_type: elevenlabs`. (§6)
11. **Privacy switches**: `record_voice: false`, an explicit `retention_days` (not 0), optional `DELETE` after the webhook, read the values back; ZRM eligibility is unknown. (§8)
12. **Spend and refusal path**: set `bursting_enabled`, `agent_concurrency_limit`, `daily_limit`; handle a refusal at mint and at connect. (§9)
13. **CSP origins**: `wss://api.elevenlabs.io` plus the LiveKit host, read off the spike. (§2, §4)
14. **Alternative named**: Speech Engine as the V2 option; `api_type: websocket` is undocumented. (§11)
15. **Cost**: custom LLM fee unknown; read `charging` on the spike. (§9)

## Outdated thinking in the draft

Most of the 3 Oct draft reads as current: a token minted on the server, a custom LLM door that streams only the `say`, the thread as the record, the trace spoken as buffer words, typing leaving voice, audio off and the least retention, WebRTC by default, and a spike before anything is kept all match the sources. Six points are stale or unsupported and should be corrected before build: a dynamic variable is not documented as templating into `elevenlabs_extra_body` (the extra body is its own `custom_llm_extra_body`, behind its own toggle, and the SDK option names are undocumented); an allowlist and signed tokens should not be combined on one agent; "language detection on" with "tools ignored" is self-contradictory because the tool only acts when the door returns a function call; "about 1 s per the vendor" is on no page; ElevenLabs may send several requests per turn and retries a failing custom LLM at least 3 times, so the door must dedupe and never end a stream empty; and Speech Engine is a documented first-party alternative the draft does not name, while `api_type: websocket` exists with no protocol page. Everything else is a refinement, not a reversal.
