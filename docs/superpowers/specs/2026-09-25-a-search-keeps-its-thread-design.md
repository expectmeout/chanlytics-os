# A search keeps its thread: design spec

**Date:** 25 Sep 2026 · **Owner:** Ruben · **Status:** built, one PR · **Base:** `origin/main` at `beb1f342` (#1009). Follows `2026-09-24-ask-answers-a-search-design.md`, whose section 5 left "a thread id on a search" unbuilt. Where this spec and the code disagree, the code wins.

## 1. Problem

A search is planned in Ask as one turn: the owner describes businesses, the model proposes `propose_lead_search`, the card is approved and `POST lead-searches` makes the search. When the search's probe later stops to ask its question, the Leads answer row answered it through `leadAnswerPlan` with `threadId: null`. So:

- every answer opened a **new** Ask thread, and a thread is titled by its first message (D9), so Ask's Earlier list filled with titles like "On People › Leads, my search for Pilates studios · Denver (search id 2820ac8f-…) stopped to ask: …": machine text with a UUID in it;
- the stored user message **was** that machine sentence, not what the owner typed;
- the model answering could not see the conversation in which the owner planned the search.

## 2. Decisions

- **T1. A search keeps the thread it was planned in.** `lead_searches.thread_id` (00172): nullable, a foreign key to `ask_threads` with `on delete set null` (a thread deleted, or dropped by `purge_ask` after ninety days, takes the link and never the search), a partial index for that set null. `lead_search_create` takes `p_thread_id uuid default null` and keeps it only when the thread is the caller's own in the same workspace (00040: a thread is one person's); anything else is null, never a refusal. Every search made on the page, and every search before 00172, keeps null. `lead_searches_view` appends `thread_id` last.
- **T2. The card carries its thread.** The Ask route stamps `payload.thread_id` (the turn's thread) on every new-search `lead_search` card it returns and stores; a card that answers a search (`amends`) carries none. `commitProposal` posts it beside the plan (`{...plan, thread_id}`); `POST lead-searches` reads it through a route-local schema, drops one that is not an id, never stores it in the plan, and names `p_thread_id` to the door only when there is one, so a search from the page calls the door exactly as before.
- **T3. The DTO carries it; the answer row sends it.** `LeadSearchDto.thread_id` (`toSearchDto`); the Leads page's `answerOf(s)` passes it as `threadId`, and `leadAnswerPlan` sends `{ text: <the owner's words>, threadId, answering: { searchId }, surface: "leads" }`.
- **T4. The owner's words in the thread; the context beside them.** The client no longer writes the machine sentence (`leadFinderAmendAsk` is gone). The route reads the search named in `answering` (`searchRow`, under RLS, in this workspace; a search elsewhere is a 404 before anything is saved), and stores the user turn as `{ text: words, answering: { search_id, name, question, asked, leaving_out } }` in `ask_messages.content`: no new column, since `content` is already the turn's JSON. The model reads `askTurnText(words, answering)`, the same sentence the client used to send, on this turn; and `readThread` rebuilds it for every stored user turn (`modelTurnOf`), so a later turn's history (`foldHistory`, 12 turns of 1,200 characters) still says what that answer was about. The fields are clipped (name 80, question 300, asked 200, eight exclusions) so the words survive the history's cut. It is stored rather than re-read from the search on each later turn because the search moves on (its plan is amended, its question answered): the turn should say what was true when it was answered. The Line reads `text` only, so the page, copy, search and the thread list never see the context.
- **T5. The fallback.** A `thread_id` the caller cannot read (a teammate planned the search: RLS returns nothing for another person's thread; or it is gone, or in another workspace) is not an error for an answer: the route starts a thread of the caller's own. A plain question to such a thread is still the 404 it always was.
- **T6. The title of a thread an answer starts is the search's name** (`titleFromSearch`), e.g. "Pilates studios · Denver", not the owner's words. An answer is usually a reply ("Yes, include them") that says nothing alone in Ask's list; the search's name is how the Leads rail names it, is the owner's own (they can rename it), and is what they will look for. The machine sentence never becomes a title: it is never the stored text.

Keep and Stop from Ask stay a deliberate no (recorded in the earlier spec): one press on the question strip, which every door lands on.

## 3. As built (25 Sep 2026, one PR)

- Migration `00172_a_search_keeps_its_thread.sql`: the column, its index and comment; `lead_search_create` dropped at four arguments and made again at five (00140's body plus the thread check), its comment and grants restated; `lead_searches_view` replaced with `thread_id` appended. `database.types.ts` regenerated from a replay.
- Server: `app/api/v1/ask/route.ts` (`answering`, the fallback, the title, the card's thread), `server/ask/prompt.ts` (`SearchAnswering`, `answeringOf`, `askTurnText`, `titleFromSearch`), `server/ask/store.ts` (`modelTurnOf`, `readThread().turns`), `app/api/v1/lead-searches/route.ts`, `server/leads.ts` (`thread_id` on the row and the DTO).
- Client: `legacy-bridge/ask/api.ts` (`answering` on send), `legacy-bridge/ask/commit.ts`, `legacy/pages/leads-finder.jsx`, `legacy/pages/clients-a.jsx`. No new button, badge or label.
- Tests, all executed: `ask-routes.test.mjs` (the answer lands in the planning thread with the owner's words, the model reads the context on that turn and a later one, the fallback and its title, a foreign search refused, the card's thread), `lead-routes.test.mjs` (the route hands the door the thread and never the plan; the DTO carries it), `lead-ask.test.mjs` (the commit posts it), `leads-finder.test.mjs` and `leads-honest.test.mjs` (the answer row sends the words, the thread and the search), `lead-search-thread.db.test.mjs` (the door keeps only the caller's own thread in the workspace; set null when the thread goes; a teammate's thread is invisible to the session client).
- Deploy order: apply 00172 **before** the dashboard deploys: the new route names `p_thread_id` for an Ask card, which the four-argument door does not take. A search from the page works in either order.
- Not built: a search made before 00172 (or on the page) gets no thread written back when its first answer starts one, so each later answer to it starts another thread titled by its name. Writing it back needs a door on `lead_searches` of its own; not needed until that repeats in practice.
