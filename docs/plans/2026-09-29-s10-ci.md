## 1. Main is verified after every merge

- `ci.yml` and `database.yml`: a pull request's runs share a group and the newer cancels the older; a push to main
  gets a group of its own commit, so no merge's run is cancelled and none waits to be replaced by the next one (a
  queued run in a shared group is cancelled by a newer one even with `cancel-in-progress: false`).
- `database.yml` asks its question of everything since the last main commit whose replay passed (read from the runs'
  history), not only of its own push, so a replay that was cancelled, failed on the runner or never started is made up
  by the next push (defect 62). An unreadable history replays from zero. The question is `checks/replay-range.mjs`'s,
  run over a repository made in the test.
- Both workflows answer `merge_group`, so a merge queue works the day it is turned on.
- A push to main checks the subject that landed against the title rule, that it carries `(#N)`, and that it is not a
  merge commit; a break opens a warning issue (I2:1, B2:4, defect 60's detector). `pr-title.mjs` gains
  `landedProblems`.

## 2. Applied migrations cannot change, and production cannot lag in silence

- `supabase/migrations-ledger.json`: every migration main carries, in the order production applies it, with the
  checksum of its text (line endings normalised). `migrations.test.mjs` holds it: an edited, renamed or deleted file
  fails; a file not in the ledger fails with the command that records it; the ledger's order must ascend, so a file
  numbered below the head cannot be recorded; and the numbers are contiguous below the head but for the gaps it
  argues. The old "numbers only go up" test compared a sorted list with itself and could not fail (defect 59); it goes.
- `tooling/scripts/checks/migration-ledger.mjs`: `--record` appends new files above the head (and says each entry it re-hashed); `--compare` reads
  production's ledger (`supabase migration list` output pasted or piped, a list of versions, or the database named by
  `SUPABASE_PROD_READ_URL`) and says what main has that production lacks, and the reverse, with how long each has
  been on main.
- 00280 `public.migration_head()`: the newest applied version and how many, security definer, executed by the
  service role only. Keyed `/api/diag` answers it under `migrations`.
- `.github/workflows/migration-ledger.yml`: weekly, off until `SUPABASE_PROD_READ_URL` is set; when main has been
  ahead of production for a day it keeps one issue open and pages through the edge's pager door.
- `docs/runbook.md`, "Apply a migration" rewritten to the practice the lanes follow (who applies, from where, a dry run
  first, a number above production's head, never `--include-all`), with the ledger compare as a release step.

## 4. Release and rollback

- `.github/workflows/release.yml`: every push to main tags `vYYYY.MM.DD-<sha>` and publishes a release whose note is
  the pull requests merged since the last tag (`tooling/scripts/ops/release-note.mjs`).
- The edge names its build: `GET /api/version` answers `VERCEL_GIT_COMMIT_SHA`, read through `env.ts`.
- The edge's pager has a door: `POST /api/admin/page`, the platform's key only, a closed set of conditions (the
  nightly red twice, production behind main), one page per condition per six hours as every page.
- `docs/runbook.md`: a rollback rehearsal (promote the previous deployment of each project, what a migration means for
  it, the config-compatibility rule) and the release steps.

## 5. The nightly

- One rolling issue instead of one a night: a red night comments on the open one, a green night closes it; the first
  run folds the old per-night issues into it. The second red run in a row pages (`tooling/scripts/ops/rolling-issue.mjs`).
- `workflow_dispatch` takes `credential_free_only` and `base_url`, so the credential-free specs run alone, against an
  address that needs no bypass too (a protected preview is `preview-smoke.yml`'s).
- The Ask day step tells "crossed a line" (exit 1) from "could not run" (exit 2: a missing variable or a crash) and
  titles its issue by which (I2:2).
- Defect 61: the two reach-out cron door tests clear the database variables before they ask for no database.
- For the tests lane: a node-suite leg under `TZ=Pacific/Auckland`, and a smoke of the credential-free specs against a
