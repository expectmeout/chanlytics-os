## 1. The dashboard reads its environment once

**Built** (both apps validate at boot; a production edge or dashboard missing a required variable refuses to serve).

Today the dashboard reads `process.env` 49 times in 23 files, and neither app checks its environment at boot.

- `apps/dashboard/src/server/env.ts`: one zod schema over every server variable, read once, each value trimmed and
  blank as unset, with typed getters named for what they give (`edgeUrl()`, `supabaseServiceKey()`, …). A variable a
  production deployment cannot serve without is `required` in production (`VERCEL_ENV === "production"`), and a
  missing one is named by `productionProblems()`.
- `apps/dashboard/src/lib/public-env.ts`: the browser's `NEXT_PUBLIC_*` values, each read by its literal name so
  Next inlines it at build, and nothing else. Browser code imports only this one.
- A lint rule (`no-restricted-properties` on `process.env`, as the edge's) makes a read anywhere else under
  `apps/dashboard` (server, app, the root's `proxy.ts`, `next.config.ts`, `instrumentation.ts`) an error.
- `env-manifest.test.mjs` holds `env.ts` plus `public-env.ts` and `apps/dashboard/.env.example` to one list, as it
  does the edge's.
- The production URLs written as code defaults (the edge's URL in `src/server/edge.ts`, the dashboard's origin in
  `dashboard-origin.ts`, the lead wires' base in `lead-wires.ts`, the public origin in `origin.ts`, the voice shell's
  origin in `voice-shell.ts`) become required in production: a preview or a laptop keeps a default where one is
  harmless, and production refuses to boot without its value.
- Both apps validate at boot in `instrumentation.ts` (`register()`): the dashboard through `env.ts`, the edge through
  its own `env.ts` (a `productionProblems()` there). A production boot missing a required variable logs one line,
  `env_invalid` with the names (never the values), and throws, so the deployment fails its first request loudly rather
  than on the first use of a missing secret. Tests run `register()` over a production environment with a hole.

## 2. Security switches fail closed, with sunsets

**Built.** No second registry: the switches are rows of the AI lane's `packages/contracts/src/ai/flags.ts`, one entry
each with its day. That registry gained a `rollout` mechanism, a `weaker` block (the weaker mode a switch allows, the log
event that proves the world is ready to close it, and what closes it) and `daysToSunset()`.

- The rows: `RETELL_DOORS_SIGNED` (17 October 2026; no longer "kept"), `RETELL_FN_SECRET`, `RETELL_WEBHOOK_KEY`,
  `DIAG_KEY`, `GOOGLE_OAUTH_STATE_SECRET` and `EDGE_TOKEN_UNBOUND` (13 October 2026: the tokens that name no body).
- `flag-registry.test.mjs` holds each row to an owner, a day (or the reason it is kept) and its weaker mode's
  evidence, and fails the build a month after a switch's day; the edge's switches are checked against `env.ts` getters
  documented as switches. The edge's `securitySwitchesHere()` reports which weaker modes are open on the deployment it
  runs in, in `/api/diag`'s `securitySwitches` section, so the 3 October read starts from what each deployment allows.
- Fail closed: any set value of `RETELL_DOORS_SIGNED` but an explicit off (`0`, `false`, `off`, `no`) is signature-only,
  so a "true" typed by someone who meant to close the doors closes them. In production the dashboard refuses to sign
  an OAuth state with `DIAG_KEY` (section 1's boot check names `GOOGLE_OAUTH_STATE_SECRET`).
- Not flipped, and nothing here can flip them: `RETELL_DOORS_SIGNED=1` after Ruben's 3 October read of
  `voice_door_auth`, and `EDGE_CALL_SECRET` on previews.

## 3. Edge tokens: a nonce that is checked, a body that is bound, a workspace on every door

**Built.** `authorizeAdmin` (`apps/edge/lib/admin-auth.ts`) is async and keeps the checks the token was minted for.

- A nonce is remembered per instance (bounded at 10,000, each until its token expires) and a token seen again is
  refused `token_replayed`. A token that carries a body hash (`bh`) opens the door for that body only (`token_body`),
  against the raw body a door read once (`readBody`, the defects lane's). An older dashboard's token without `bh` is
  let in and logged `edge_token_unbound` until `EDGE_TOKEN_UNBOUND`'s day, so either deploy order works.
- Every door names a workspace and a person. The dashboard's `callEdge` now REQUIRES both (`workspace`, `user`, each a
  string or an explicit null, no default), and 14 routes that used to send none send `ctx.userId`; the edge takes the
  token's person before the body's (`personFor`) and the token's workspace before the body's (`workspaceFor`), and
  refuses a body that names another. The live-call doors (whisper, stop-call, steer, hand-over) check that the call or
  the draft belongs to the token's workspace before acting. `voice-converge` converges every workspace's agent, so it
  is the platform's alone: a token that names a workspace is refused `platform_only`.
- Tests: a replay, a changed body, another workspace's call id, a token with no person, and a dashboard call that names
  no caller (`dashboard-names-its-callers.test.mjs`), each refused.

## 4. A fresh session before the sensitive acts

**Built.** `fresh: true` is declared on 13 routes (account deletion, a member's role change and removal, an invite, export three ways, erase a person or a lead, and billing's four); `requireFreshSession` refuses a session the Auth server no longer knows with 401, and answers 503 `upstream_auth` when it cannot ask, so a revoked session is never mistaken for a live one. The session cookies carry `sameSite: lax` and `secure` on https (`lib/supabase/cookie-options.ts`, one place for the server client, the proxy and the browser client).

`getClaims()` verifies the JWT locally, so a revoked session passes until it expires.

- A route may declare `fresh: true` in its policy; `withRoute` then asks `getUser()` (the auth server) before the
  handler runs, and a session the server no longer knows is refused 401. Erase (a person, a lead), export, a role
  change, billing and account deletion declare it; `route-policy.json` pins each declaration through the existing test.
- The session cookies: `secure` in production and `sameSite: lax` where `@supabase/ssr` lets us set them; `httpOnly`
  is not possible while the browser client reads the session from the cookie (the shell's realtime and Ask use it),
  which the plan records rather than breaks.

## 5. The database: INSERT fences and tenant-true parents

**Built** as 00283, 00284 and 00285 (placeholders: the controller renumbers; wave 1 took 00270 to 00275).

- 00283: `grant insert (columns…)` on each session-writable table, like 00121's UPDATE fences, so a session cannot
  write a column the edge owns (twelve tables the census found, `messages` among them, which the defects lane's policy
  left to this); the `insert_fence` rule in `privileges.db.test.mjs` fails a session-insertable table with a
  whole-table INSERT grant.
- 00284: composite `(tenant_id, x) → parent(tenant_id, id)` foreign keys for 51 child columns whose parent must share
  the child's workspace. Each REPLACES the single-column key it is beside, with that key's delete rule, because a twin
  makes PostgREST's embedded selects ambiguous (PGRST201). They are added NOT VALID, so the migration takes brief locks
  and no scan; a later `VALIDATE CONSTRAINT` is the follow-up, listed in the pull request. A tenancy db test inserts a
  child pointing at another workspace's parent and is refused, and the catalog rule fails a child key that is not the
  composite.
- 00285 (defects 43 and 45): a partner's password opens no door a seat opens. `reach_out_lead_timeline`,
  `partner_invitations_mine`, the invitations read policy and `partner_invite_decline` ask for the second factor
  (`session_shows_second_factor()`); `session_has_partner_seat()` lets the dashboard say "second factor required" to a
  partner whose seat is hidden until then. `partners/second-factor-catalog.db.test.mjs` walks the catalog, so a new
  definer door that reads a seat without the gate fails.

## 6. SSRF: resolve, then refuse

**Built.** `packages/channels/src/public-fetch.ts` (`publicFetch`, `isPublicAddress`): the socket's own lookup is replaced by one that refuses any address that is not public, every redirect hop is connected to through it, and a literal address is judged before a socket is made. It is the fetch of the calendar feed (preview and availability), Ask's openings, the listing check and the lead wires' page reads. Suites that stand in for the network do so with `setPublicFetch`, preloaded by `tooling/scripts/tests/calendar/_stand-in-network.mjs`.

`feedUrlOk` checks the hostname string, so a public name that resolves to a private address passes. Every server-side
fetch of a user-supplied URL (the calendar feed, the business website read, lead pages) goes through one guarded fetch:
https only, the name resolved and every address refused if private, loopback, link-local, CGNAT or metadata, at
connect time (a `lookup` on the agent, so a rebinding between check and connect cannot pass), and each redirect hop
checked again. Tested with a fake resolver.

## 7. `tenantDb(tenantId)` on the edge, and the cross-workspace checklist

**Built.** `packages/db/src/tenant-db.ts` (`tenantDb`, `platformWide`) scopes every select, update and delete it builds

`line-resume`, `line-release`, `line-provision-job`, `lines.ts`'s store) and the token budget now run on it.

The checklist: the backend map scored 51 modules under 50% likely to be scoped to one workspace, and each was read.

- **By design (32)** carry a header line `Cross-workspace: <why it reads across workspaces>` (the edge's 18, the
  dashboard's 5, the packages' 9): sweeps, provider webhooks that name their workspace by id, the platform's back office.
- **Already scoped (19)**: the statements filter or stamp `tenant_id`, or the caller proves the row first.
- **Must scope**, each fixed with a test that fails on main (`lines-writes-name-the-workspace.test.mjs`,
  `lead-tell.test.mjs`, the door tests): the lines saga's writers (they wrote a line by its id alone), the token budget

- The ratchet: "edge statements that name no workspace" (`workspaceless.json`, a row in `docs/debt.md`) counts the

  variable the tree cannot follow, or an upsert keyed by `tenant_id`, and the pull request lists the modules.

## 10. MFA for owners and platform admins (Ruben's decision)

**The design, for acceptance; nothing here changes a session.** The pieces exist for partners (decision 0013): Supabase
Auth holds the factor, the token's `aal` claim says whether the session showed it (`secondFactorShown`), the database
asks in `is_acting_member` and `caller_has_permission`, and `/verify` is the step.

- What it would cover, counted on `route-policy.json` (203 routes): 21 owner routes (14 writes, 7 reads), 11 platform
  routes and the 13 `fresh: true` acts of section 4. An owner's seat would need the factor the way a partner's does
  (`seatNeedsSecondFactor(role)` widens from `partner` to `partner` and `owner`), the platform's back office would
  ask for it before any of its 11 routes, and sign-in would send an owner without a factor to enrol once.
- What it costs: every existing owner enrols an authenticator before the day it is on (a sign-in that is refused
  until then is a locked-out customer), so it ships behind a per-workspace date, with the email code as recovery.
- What Ruben decides: yes or no; owners now or from a date; whether the platform's admins are first (11 routes, a
  handful of people, the cheapest and the riskiest to leave).
