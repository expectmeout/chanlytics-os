Chanlytics · Platform audit

Agent Store & Studio on A2A + AG‑UI

Surfaces: agent-store.jsx · agent-studio.jsx Concept: operators connect external agents (A2A); the portal fronts them to users (AG‑UI); the Store makes them installable by others Refs: AG‑UI docs · A2A purchasing-concierge codelab

The good news: Chanlytics already behaves like an AG‑UI client without knowing it. The gap is entirely on the supply side — both surfaces assume every agent is first‑party, so there is no way to connect an external agent, no publisher, no trust model, and no handshake. That's what Store and Studio need to gain.

01Protocol → surface map

A2A

agent ↔ agent · how an external agent joins

An agent is discovered by its Agent Card (name, skills, capabilities like streaming, auth scheme); the portal delegates tasks to it and receives streamed results.

User-visible in exactly two places: Studio's connect flow and a Store listing's provenance line.

AG‑UI

agent ↔ user · how the UI talks to any agent

16 event types. Chanlytics already renders them: Inbox approvals = interrupts, Live transcript = TEXT_MESSAGE_*, Tasks ledger = TOOL_CALL_*, session stores = STATE_DELTA.

Raw face visible in exactly one place: Studio's test bench. Everywhere else it stays plumbing.

MCP

agent ↔ tools · what an agent can touch

Tools and integrations an agent uses (Square, Gmail, calendar). Already surfaced as the "Connects:" requires-line and Admin → Integrations.

No new UI. Keep it as the requires-line; never a config surface here.

02Verdict: is AG‑UI needed?

Yes — keep it, but as plumbing, not a feature. AG‑UI is the contract that matches what the product already does: ask-first approvals are literally protocol interrupts, live calls are message streams, the confidence dots ride on run metadata. Adopting it costs no new consumer UI — which is the strongest evidence the architecture fits.

Never print protocol names on consumer surfaces. A studio owner buys outcomes. Store cards say "Streams live · Asks before acting · Syncs state" — capability badges derived from the Agent Card — not "AG‑UI compatible." Protocol vocabulary (endpoints, cards, event traces) is allowed only inside Studio, which is the workspace's one developer-facing room.

A2A is the marketplace enabler and earns limited visibility. The Agent Card is a real artifact operators will paste and inspect, so "External · via A2A · by <publisher>" on listings is honest provenance, not jargon.

03Store — from catalog to two-sided marketplace

Today the Store is a one-sided list of first-party templates (glyph, ability chips, proof line, credits, install modal). Nothing identifies who made an agent, what it's allowed to touch, or how it connects. Five gaps:

S1Provenance layerBuild

Every listing gets a publisher: Chanlytics (first-party) or a community publisher with a verified badge and an External · via A2A tag. Filter chip row gains "First-party / Community". Cards without provenance are the reason the current store feels like a settings page, not a market.

S2Capability badges from the Agent CardBuild

Derive plain-English badges from card capabilities: Streams live (streaming), Asks before acting (interrupts/HITL), Syncs state (shared state), Hands off to your fleet (A2A delegation). Extends the existing ability chips; never shows protocol names.

S3Install = handshake, not toggleBuild

For external listings the install modal gains a Connection section — endpoint host, auth scheme, what data leaves the workspace — and install runs a visible 3-step handshake (fetch card → check capabilities → apply autonomy default) before the agent lands in Fleet tagged with its source.

S4"Your listings" — the publisher sideBuild (thin)

A tab for agents you connected and published: installs count, listed/unlisted state, "manage in Studio" link. This is the half that makes the marketplace two-sided; thin is fine (no payouts UI yet).

S5Trust floor on external listingsBuild (copy-level)

One quiet line the modal always shows for community agents: workspace guardrails and quiet hours apply regardless of publisher; kill switch lives in Fleet. Honesty rule: an installed external agent must actually appear in Fleet (session write-through, same pattern as segments → clients).

04Studio — gain the connect path

Today Studio only composes native agents from parts. The concept requires it to also be the door external agents walk through. Four gaps:

D1Two modes: Compose · Connect externalBuild

Connect flow: paste endpoint URL → fetched Agent Card preview (name, skills, capability badges, auth scheme) → permission mapping (channels it may use, guardrail set, autonomy contract — reusing the existing chips) → test bench → Add to Fleet and optional Publish to Store. Compose keeps its current builder untouched.

D2Test bench with event traceBuild

Run one scripted sample task against the connected agent and show the run as an inspectable trace — RUN_STARTED → TEXT_MESSAGE_CONTENT → TOOL_CALL_* → STATE_DELTA → RUN_FINISHED — with the reply rendered beside it. The single place raw protocol is visible; doubles as the "did the handshake actually work" proof before Fleet.

D3Publish flow → StoreBuild (thin)

Listing draft (name, role line, price in credits) with a review state (submitted → listed) that writes into S4's "Your listings". Proof lines stay earned — new listings show "No track record yet," never invented stats.

D4Honest wiring for both pathsBuild

Publishing (compose) and connecting (external) both push a session agent into Fleet via a store + window event (store:installed pattern), so "Custom agents: 2" and the Fleet roster stay truthful — same contract discipline as the rest of the app.

05Deliberately not building

  • Skip MCP tool-config UI — tools remain the requires-line + Admin → Integrations.
  • Skip Protocol names in nav, store cards, or marketing copy anywhere outside Studio.
  • Skip A separate developer portal — Studio is it.
  • Skip Payouts/monetization for community publishers — out of scope for this pass.
  • Skip Raw event consoles on Fleet/Live/Inbox — those pages already render the events as product UI.

Recommended order: D1 + D2 (the connect path is the concept's spine), then S1–S3 (marketplace face), then S4 + D3 (two-sided loop), with D4/S5 woven through each.
