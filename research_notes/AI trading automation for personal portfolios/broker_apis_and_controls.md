## Key question 1: Which US equities brokers can a normal retail person actually get API access to, how, and how long does it take?

### Takeaway

Alpaca, Interactive Brokers, Tradier, tastytrade, Public.com, Webull and Schwab all give an individual programmatic trading access without a business relationship; Alpaca and Tradier are instant for paper/sandbox, Webull quotes 1-2 working days, Schwab needs two sequential "a couple of days" approvals, IBKR's OAuth 2.0 is still beta and individuals practically use the local Client Portal Gateway or TWS/IB Gateway. Robinhood has no official equities API; E*TRADE's OAuth 1.0a API still works but lacks bracket orders.

### Cited Findings

- Alpaca: "when you create an Alpaca account, your account is a paper trading account by default. Anyone globally can create a paper only account by signing up with their email address... To enable live trading from a Paper Only Account, you need to go through an account on-boarding process with Alpaca Securities LLC, a FINRA member and SEC registered broker-dealer" — [Alpaca docs, Trading Account plans](https://docs.alpaca.markets/docs/account-plans)
- Alpaca "provides access to trading Equities, Options, and Crypto for clients in over 30 countries"; individual taxable accounts only, no retirement accounts; Canadian individual accounts targeted for regulatory approval around November 2026 — [Alpaca docs, account opening](https://docs.alpaca.markets/docs/account-opening); [Alpaca forum, Canada](https://forum.alpaca.markets/t/is-the-market-data-subscription-available-in-canada/19519)
- Alpaca Trading API rate limit: "200 requests per minute, per account"; 429 when exceeded; headers X-Ratelimit-Limit/Remaining/Reset; "Alpaca Plus which, for a fee, allows increased rates (up to 1000/minute)" — [Alpaca forum, Trading API limitations](https://forum.alpaca.markets/t/trading-api-limitations/9743)
- Alpaca's API trading "grew nearly 4x in Q1 2026, largely driven by AI, as new CLI & MCP Server provide direct, efficient access" — [Alpaca blog tag: ai trading](https://alpaca.markets/blog/tag/ai-trading/)
- Interactive Brokers: "Interactive Brokers is merging web-based API products into a single IBKR Web API, accessible by OAuth 2.0. OAuth 2.0 is in beta and supports first-party (accessing one's own accounts) and third-party usage"; "only supports private_key_jwt client authentication"; existing Client Portal Gateway "endpoints and authentication schemes are not deprecated and will continue to receive features and updates" — [IBKR Web API OAuth 2.0 introduction](https://www.interactivebrokers.com/docs/web-api/authentication/oauth-2/introduction); [IBKR Web API trading page](https://www.interactivebrokers.com/campus/ibkr-api-page/web-api-trading/)
- IBKR: "For retail and individual clients, Authentication to the WebAPI is managed using the Client Portal Gateway, a small java program used to route local web requests with appropriate authentication"; the older OAuth (1.0a) flow is "for licensed Organizations, Financial Advisors, and IBrokers" — [IBKR Web API introduction](https://www.interactivebrokers.com/docs/web-api/web-api-v-1-0-documentation/introduction)
- IBKR Web API pacing: "global request rate limit of 50 requests per second for each authenticated username"; "Users making requests via the CP Gateway tool are restricted to 10 requests per second"; brokerage session times out after 5 minutes without requests, call `/tickle` about every minute — [IBKR Web API pacing limitations](https://www.interactivebrokers.com/docs/web-api/trading/usage-and-availability/pacing-limitations); [IBKR authentication FAQ](https://www.interactivebrokers.com/docs/web-api/authentication/faq)
- Tradier: sandbox "is a paper trading account to test your integration with the API, including working with delayed market data and paper trades"; "Tradier delays its market data by the industry standard 15 minutes"; rate limit "120 requests per minute (Basic), with higher limits available"; OAuth "Tokens expire in 24 hours, but if you need continuous access... refresh tokens can be enabled. There is an approval process that requires emailing the Tradier support team" — [Tradier docs FAQ](https://docs.tradier.com/docs/faq); [TradersPost Tradier page](https://docs.traderspost.io/docs/all-supported-connections/tradier)
- Tradier pricing: Tradier Pro "$10/month" for commission-free stock and options; Pro Plus $35/month; single-listed index options $0.35/contract plus fees; API access included on the Standard plan — [Tradier options plan page](https://trade.tradier.com/options); [Tradier promotional page](https://trade.tradier.com/brokerchooser)

- Public.com: "The API is now available to all Public members—no approval required"; "free to use"; "Trading in stocks, ETFs, options, crypto and index options"; "Support for fractional and whole-share equity trades, up to 16 hours per day"; "The Public Individual API is for your own personal, non-commercial use"; generate key at "Account Settings > Security > API"; Python SDK — [Public.com API page](https://public.com/get/api); [Public.com, what is a trading API](https://public.com/learn/what-is-trading-api)

### Inferences

- For a retail person who wants to start today, the practical ladder is: Alpaca paper (instant) -> Tradier sandbox (instant) -> tastytrade cert (after self-service OAuth app) -> Public (instant key, no sandbox) -> Webull (1-2 days) -> Schwab (two reviews, no sandbox) -> IBKR (account approval, then local gateway software; OAuth 2.0 direct-to-api.ibkr.com for individuals is still beta).
- IBKR and Moomoo are the only ones that require you to keep a local process (TWS/IB Gateway/CP Gateway, OpenD) alive, which matters for an unattended agent.
- Schwab's 7-day refresh token and E*TRADE's three-legged OAuth 1.0a both require a human to re-authorise periodically; Alpaca, Public, Tradier (personal token) and Kraken/Coinbase keys do not.

### Gaps

- Exact live-account approval times for Alpaca, IBKR, Tradier and tastytrade were not found in reachable sources.
- Whether IBKR's OAuth 2.0 first-party flow is self-service for individual accounts in October 2026 could not be confirmed (docs blocked; the Web API intro page still routes individuals through the CP Gateway).
- Robinhood's "Agentic Trading" (2026) appeared only in a search extract of a third-party page; the launch, scope and whether it exposes stock order placement to third-party agents could not be verified.
- Public.com API rate limits, launch date and sandbox availability were not retrievable.
- Webull OpenAPI's exact order-type coverage (vs the app's) and rate-limit numbers were not retrievable.

## Key question 2: Which brokers offer server-side protective features (kill switches, trading toggles, precautionary limits), and what exactly do they do?

### Takeaway

Only two equities brokers offer something an owner can set that the API cannot talk its way past: Alpaca's account configuration flags (`suspend_trade`, `no_shorting`, `max_margin_multiplier`, `max_options_trading_level`) and IBKR's Precautionary Settings plus order-reply confirmations; but IBKR's protections can be bypassed for API orders by a TWS setting or a Web API suppression call, so the owner must deliberately leave them on. No equities broker surveyed exposes a per-order or daily notional cap on an API key; the only notional cap found is client-side, in tastytrade's official MCP server.

### Cited Findings

- Alpaca Account Configuration fields (from the official Python SDK source): `suspend_trade`: "If true Account becomes unable to submit new orders"; `no_shorting`: "If true then Account becomes long-only mode."; `max_margin_multiplier`: "A number between 1-4 that represents your max margin multiplier"; `fractional_trading`: "If true, account is able to participate in fractional trading"; `max_options_trading_level`: "0=disabled, 1=Covered Call/Cash-Secured Put, 2=Long Call/Put, 3=Spreads"; `trade_confirm_email`: "Controls whether Trade confirmation emails are sent."; `ptp_no_exception_entry`: "If set to true then Alpaca will accept orders for PTP symbols with no exception."; `dtbp_check` and `pdt_check`: "Deprecated; removed from Alpaca responses on 2026-07-06" — [alpaca-py trading/models.py](https://raw.githubusercontent.com/alpacahq/alpaca-py/master/alpaca/trading/models.py)
- Alpaca: "The effective options trading level of the account is the minimum between account options_approved_level and account configurations max_options_trading_level"; the configuration "allows a user to downgrade to a lower options trading level" — [Alpaca docs, options trading](https://docs.alpaca.markets/us/v1.1/docs/options-trading); [Alpaca docs, update trading configurations](https://docs.alpaca.markets/us/reference/patch-patch-v1-trading-accounts-account_id-account-configurations)
- Alpaca account status fields: `trading_blocked`: "If true, the account is not allowed to place orders."; `transfers_blocked`: "If true, the account is not allowed to request money transfers."; `account_blocked`: "If true, the account activity by user is prohibited."; `trade_suspended_by_user`: "If true, the account is not allowed to place orders." — [alpaca-py trading/models.py](https://raw.githubusercontent.com/alpacahq/alpaca-py/master/alpaca/trading/models.py)
- Alpaca on what a leaked key can do: "An unauthorized party with your API key pair can submit orders, cancel open orders, liquidate positions, and query portfolio telemetry within the limits of your account's available cash and buying power. However, direct Trading API keys cannot initiate ACH bank deposits or request wire withdrawals." — [Alpaca Learn, API key security best practices](https://alpaca.markets/learn/api-key-security-best-practices-for-alpaca-builders)
- Alpaca OAuth2 scopes (for third-party apps, not first-party keys): "read-only endpoint access assumed by default"; `account:write` "Write access for account configurations and watchlists"; `trading` "Place, cancel or modify orders"; `data` "Access to the Data API" — [Alpaca docs, Using OAuth2 and Trading API](https://docs.alpaca.markets/docs/using-oauth2-and-trading-api)
- IBKR Precautionary Settings: "Precautionary values are used by the system as safety checks. If you submit an order that violates any of these custom settings, you will have to confirm your intent to transmit the order before TWS submits it."; thresholds "set in terms of percentage or the number of ticks outside of the NBBO (settings may also be defined in terms of share/contract quantity or total dollar value of trade)"; categories: Percentage ("safety net to prevent you from transmitting a limit order that has a mistyped limit price"), Size Limit ("Limits the value in the Quantity field"), Total Value Limit ("if you transmit an order with a price that exceeds the total dollar amount you specify, you will receive a message... and you must confirm"); "This setting does not prevent orders from being submitted but rather controls when a warning message will appear" — [IBKR KB 838, Order Price Relative to the Market](https://ibkb.interactivebrokers.com/article/838); [IBKR KB 1299, percentage constraint message](https://ibkb.interactivebrokers.com/nl/node/1299); [IBKR TWS guide, Define Precautionary Settings](https://www.interactivebrokers.co.uk/en/software/tws.bak/usersguidebook/configuretws/define_precautionary_settings.htm); [IBKR Campus, configuring TWS presets](https://www.interactivebrokers.eu/campus/trading-lessons/configuring-tws-presets/)
- IBKR TWS API bypass: under "Global Configuration" > "API" > "Precautions" a user can enable "Bypass Order Precautions for API orders" and other bypasses (bond warnings, "same action pair trade", "price-based volatility risk warning", "US Stocks market data in shares warning", "Redirect Order warning for Stock API orders", "No Overfill Protection precaution") — [IBKR TWS API docs, Order Precautions](https://www.interactivebrokers.com/docs/tws-api/doc/tws-settings/order-precautions)
- IBKR Web API: "The /iserver/reply endpoint is used to confirm order precautions and warnings presented from placing orders. Orders must be replied to immediately after receiving the reply message, and submitting other orders or other requests will cancel the order"; "Users that wish to avoid receiving /reply message should consider using the Suppression endpoint to automatically accept them. The /iserver/questions/suppress endpoint... POST an array of messageIDs to suppress those order message types for the remainder of the Web API brokerage session"; "after sending your initial confirmation... you may receive additional reply messages which must also be responded to before the order will submit" — [IBKR Web API, Place Order Reply Confirmation](https://www.interactivebrokers.com/docs/web-api/web-api-v-1-0-documentation/endpoints/orders/place-order-reply-confirmation); [IBKR Web API, Order Reply Suppression](https://www.interactivebrokers.com/docs/web-api/trading/orders/order-reply-suppression); [IBKR Web API, Order Reply Messages](https://www.interactivebrokers.com/docs/web-api/trading/orders/order-reply-messages)
- IBKR secondary users: "The primary account holder can create a secondary username, and market data services are user-specific"; users are managed and deleted under "Users & Access Rights" — [IBKR KB 1004, Adding a second user for an individual account holder](https://ibkb.interactivebrokers.com/node/1004/)
- IBKR TWS API has no withdrawal function; money movement is by file-based instructions or Client Portal, not the trading API — [IBKR docs home](https://www.interactivebrokers.com/docs); [IBKR TWS API architecture](https://www.interactivebrokers.com/docs/tws-api/doc/architecture/the-trader-workstation/introduction)
- tastytrade official MCP server (client-side, open source): "Five tools require a confirmation token, and they are the five that submit or change an order"; "Each takes a single-use `confirmation_token` minted by its own `dry_run_*` tool, valid for 60 seconds and bound to a hash of the submitted arguments"; "`TASTYTRADE_READ_ONLY` — `1` withholds **and refuses** all 14 write and destructive tools"; pre-submit checks: "Per-leg quantities against the account's own published order-size ceilings, a notional cap on buying-power impact, and a refusal to send orders into frozen or closing-only accounts"; "`MAX_ORDER_NOTIONAL_USD` — Ceiling on an order's buying-power impact (default `50000`)"; "For an environment with no real money in it, set `TASTYTRADE_ENV=sandbox`"; "With no environment configured, this server connects to the tastytrade **production** API" — [tastytrade-mcp README](https://raw.githubusercontent.com/tastytrade/tastytrade-mcp/main/README.md)

### Inferences

- The strongest broker-side "owner limits" for an AI agent at an equities broker are (a) Alpaca `max_margin_multiplier=1` (no leverage), `no_shorting=true`, `max_options_trading_level=0`, and `suspend_trade=true` as a kill switch; (b) IBKR Precautionary Settings with Size Limit and Total Value Limit, combined with NOT enabling "Bypass Order Precautions for API orders" and NOT calling the Web API suppression endpoint, so each violating order needs a confirmation the agent can be denied; (c) a cash-only (non-margin) account anywhere, which caps exposure at settled cash.
- Alpaca's `suspend_trade` is settable through the same API the agent uses (PATCH account configurations), so an agent with the key could un-set it; it is a kill switch for the owner, not a hard boundary against the agent, unless the agent's key is the OAuth type scoped without `account:write`.
- No broker surveyed documents a per-key daily notional or loss limit; such a limit must be implemented in the owner's own gateway (the tastytrade MCP server's `MAX_ORDER_NOTIONAL_USD` is the one shipped example).

### Gaps

- Whether Alpaca's deprecation of `dtbp_check`/`pdt_check` on 2026-07-06 (after the FINRA rule change) removed any protective behaviour could not be confirmed from the docs.
- Schwab, Tradier, Public, Webull and E*TRADE: no documentation of owner-configurable pre-trade limits, trading toggles or kill switches was found; absence of evidence, not proof of absence.
- Whether IBKR Precautionary Settings apply to Web API (CP Gateway/OAuth) orders in the same way as TWS API orders (they surface as reply messages) was inferred from the reply-message docs, not stated outright.

## Key question 4: Which order types let the limit be enforced at the broker/exchange rather than in the agent's code (bracket, OCO, OTO, trailing stop, GTC limit)?

## Key question 5: Regulatory constraints an API user hits (PDT rule and its 2026 replacement, T+1, extended/24-5 hours, crypto legislation)

### Takeaway

The biggest 2026 change is that the pattern-day-trader framework and its $25,000 minimum were eliminated: the SEC approved FINRA's filing on April 14, 2026, the new intraday-margin framework took effect June 4, 2026, and brokers have until October 20, 2027 to implement it, so some brokers may still enforce PDT-style house rules in October 2026. 24/5 overnight trading is available via API at Alpaca and IBKR (limit orders), not via Schwab's or Robinhood's APIs. On crypto, the GENIUS Act (stablecoins) is law but not fully effective until final rules, and the CLARITY Act market-structure bill cleared Senate Banking in May 2026 but had not become law as of early October 2026.

## Key question 7: Security best practices the brokers themselves document for API keys and bots

### Takeaway

The brokers' own guidance converges on: least-privilege keys (trade without transfer), IP allowlists, separate paper/sandbox credentials, no secrets in code, rotation, and never exposing a local MCP/trading server to the internet; the two official MCP servers differ sharply, with tastytrade shipping dry-run confirmation tokens, read-only mode and a notional cap, and Alpaca shipping paper-by-default but no confirmation step.

### Cited Findings

- Alpaca: leaked keys "can submit orders, cancel open orders, liquidate positions... within the limits of your account's available cash and buying power... cannot initiate ACH bank deposits or request wire withdrawals" — [Alpaca Learn, API key security best practices](https://alpaca.markets/learn/api-key-security-best-practices-for-alpaca-builders)
- Alpaca MCP: "Treat your API keys as sensitive credentials. Review all actions proposed by the LLM carefully"; "do not expose it directly to the public internet with your Alpaca API keys. Use the local stdio setup from a supported desktop client"; `ALPACA_PAPER_TRADE` default `true` — [alpaca-mcp-server README](https://github.com/alpacahq/alpaca-mcp-server)
- tastytrade MCP: "Every account the supplied credentials can reach is a **real brokerage account**, and every order this server places, edits, replaces or cancels moves **real money** in it"; "Authentication is **environment-only**"; confirmation tokens, read-only flag, `MAX_ORDER_NOTIONAL_USD` default 50000, `TASTYTRADE_ENV=sandbox` — [tastytrade-mcp README](https://raw.githubusercontent.com/tastytrade/tastytrade-mcp/main/README.md)
- Coinbase: least privilege, IP/CIDR allowlist, rotate by create-and-delete, "Avoid embedding secrets directly in code; instead, use environment variables or secrets managers", "Regularly check the usage logs" — [Coinbase CDP security best practices](https://docs.cdp.coinbase.com/get-started/authentication/security-best-practices)
- Kraken: IP restriction; do not grant "Add Withdrawal Addresses" or "Withdraw Funds" to bots; GSL and Master Key; email confirmation of sensitive actions — [Kraken support, withdrawal addresses API permission](https://support.kraken.com/gb/articles/withdrawal-addresses-api-permission); [Kraken support, Global Settings Lock](https://support.kraken.com/articles/201396877-what-is-the-global-settings-lock-gsl-)
- Gemini: "Gemini recommends all API keys created be restricted to a set of Trusted IPs" — [Gemini docs, roles](https://docs.gemini.com/roles); [Gemini support, Trusted IPs](https://support.gemini.com/hc/en-us/articles/37826759865115-How-to-secure-your-API-Keys-with-Trusted-IPs)
- Binance.US: "only share API keys with trusted third-party platforms and provide the minimum level of access required"; 90-day inactive non-whitelisted keys reset to read-only — [Binance.US support, create an API key](https://support.binance.us/en/articles/9842800)
- IBKR: order precautions are on by default for API orders until the user enables "Bypass Order Precautions for API orders" — [IBKR TWS API docs, Order Precautions](https://www.interactivebrokers.com/docs/tws-api/doc/tws-settings/order-precautions)

### Inferences

- A defensible stack for "AI places bounded orders for me" in October 2026 is: a dedicated account or portfolio funded only with the agent's budget; trade-only, IP-allowlisted, expiring key where available (Kraken) or portfolio-scoped (Coinbase); cash-only/`max_margin_multiplier=1`, `no_shorting`, options level 0 at Alpaca; IBKR Size/Total Value precautions left un-bypassed; the agent restricted to bracket/OTOCO/GTC-limit order classes; and an owner-side gateway (as the tastytrade MCP server does) that enforces a per-order and per-day notional cap and a confirmation step, since no broker provides those caps server-side.

### Gaps

- Schwab, Tradier, Public, Webull and E*TRADE publish no bot-specific security guidance that was reachable.
- Whether any broker offers out-of-band (2FA/push) approval per API order was not found; none of the reachable docs describe such a feature for retail API keys.
