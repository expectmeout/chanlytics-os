Chanlytics · Component deep dive

Ask Chanlytics (⌘K)

Scope: UX/UI of the palette + the integration contract behind itDate: Jul 29, 2026

Ask is not a chatbot bolted onto the app — it is a third input device (after buttons and hotkeys) over the exact same rails. That framing decides everything below: what it should look like, and what it must never be allowed to do.

01What it is today

  • Shell-owned overlay — ⌘K anywhere; window.askAbout({prompt, answer?, links?, mode}) lets any surface open it pre-seeded (thread cards, Fleet, Billing all use it). Threads persist and resume.
  • Deterministic intent engine — ~15 regex intents (waiting-on-me, revenue pacing, segments, invoice, pause/resume agent, book Jordan, refund explainer, teach/give-task, and the four live-store intents: policy, trust, presence, compliance). Utterance → intent → answer composed at answer-time from the live stores, never canned.
  • Actions are store calls — "Book Jordan's intro call" runs IX_STORE.set(...); "Set me away" runs PR_STORE.setAway(); pause runs FL_STORE.setStatus(). Same events fire, so Inbox, Today, Tasks, Pipeline, bell all reconcile — Ask has zero private state.
  • Answers deep-link — every reply carries entity links (CHANLY.R.*), and action buttons flip to a "done" state with follow-up links.

03The integration contract

Rule 1 — thin client, always. Ask may only commit through the same store methods buttons use, so every Ask action inherits gates, events, undo, and audit for free. If an intent needs a new capability, the store gets the method first; Ask calls it second.

Rule 2 — closed intents, like closed verbs. The payload is always {intent, params} from a finite set. The ONLY machine-learning seam in the whole product is utterance → intent; execution stays deterministic. Backend swap: replace the regex router with an NLU endpoint, nothing else moves.

Rule 3 — answers read the single sources. Policy from window.POLICY, trust from RP_TRUST, presence from PR_STORE, compliance from COMPLIANCE — never restated copy. An answer is a projection, not content.

Today's code already obeys all three rules — the stress rounds proved Ask's "What can agents do?" reflected a live matrix flip, and its approve action resolved on every surface. The gaps are presentation (grouping, scope chip, governance chrome on actions), not architecture.

04Build list, in order

  • 1. Scope chip — askAbout already carries context; render it + pass it to the intent router so "approve", "snooze this", "why is this paused" resolve against the seeded thread.
  • 2. Ask · Act · Draft grouping on the try-asking list + a verb tag on each history thread.
  • 3. Governance chrome on actions — PolicyChip + gate() + Undo on committing answers.
  • 4. Result-titled threads + dedupe.
  • 5. ↑ recall of previous prompts in the composer (matches every terminal user's muscle memory).

All five are palette-local; none touch the rails. Say which to build.
